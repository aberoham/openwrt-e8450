OpenWrt E8450 Fleet Management - Changelog
==========================================

2026-08-19: IPv6 DNS Through the Gateway Restored (dnsmasq listen_address footgun)
------------------------------------------------------------------------------------
- Symptom: DNS queries to the gateway over IPv6 transport timed out entirely
  (UDP and TCP 53 both dead). Resolution still "worked" on every dual-stack
  client because resolvers silently fell back to the IPv4 nameserver — so the
  only visible cost was a timeout penalty whenever a client tried the IPv6
  server first. An IPv6-only client would have had no DNS at all.
- Root cause: dhcp.@dnsmasq[0].listen_address was set to a hardcoded list of
  addresses (loopback, LAN IPv4, the br-lan link-local, and the two Tailscale
  addresses — almost certainly added by hand during the Tailscale setup).
  When listen_address is present, dnsmasq binds ONLY those addresses,
  overriding bind-dynamic. The list never included the LAN global IPv6
  address — the very address odhcpd advertises to clients as their DNS
  server via RA/DHCPv6. Adding it to the list wouldn't stick either: the
  GUA is dynamic, derived from the ISP-delegated prefix, and changes when
  the delegation does.
- Fix: deleted listen_address outright and let bind-dynamic do its job —
  dnsmasq now picks up interface addresses as they appear, including future
  prefix changes and the Tailscale addresses the list existed to cover.
- Open-resolver check (the reason listen_address was tempting in the first
  place): bind-dynamic also binds the WAN addresses, which is stock OpenWrt
  behavior. Confirmed the fw4 wan input chain has no port-53 accept and ends
  in reject, across all WAN-side interfaces, and dnsmasq's local-service
  (still set) refuses off-subnet queries as a second layer. Verified by
  ruleset inspection from inside the network; an outside-in probe with
  scripts/test_wan_exposure.sh would close the loop but hasn't been run yet.
- Verified from a LAN client: A and AAAA lookups over IPv6 transport to the
  gateway now resolve.
- Red herring for the log: /etc/init.d/dnsmasq restart prints "udhcpc: no
  lease, failing" — that's the init script probing for competing DHCP
  servers, not DHCP breaking.

2026-08-03: Downstairs Kernel Crash #2 → pstore Recovery; Remote Syslog Added
------------------------------------------------------------------------------
- Downstairs router kernel-crashed ~26h after the 25.12.5 upgrade and
  auto-diverted to recovery mode again (same mechanism as 2026-03-20:
  kernel.panic auto-reboot + U-Boot `pstore check` → recovery initramfs)
- Both pstore dumps corrupt again (kernel: "pstore: zlib_inflate() failed") —
  deflate-compressed ramoops records don't survive this board's reset;
  crash cause remains unknown. Flow offloading ruled out (not enabled).
- Recovery: verified UBI volumes/FIT image/overlay intact, cleared pstore,
  rebooted into production. No data loss, downtime ≈ one reboot.
- New countermeasure: remote syslog from downstairs to upstairs
  (syslog-ng UDP listener writing /tmp/remote-syslog/<host>.log, RAM-backed
  on purpose — survives a sender crash without NAND wear). logd replaced by
  syslog-ng on the receiver per the OpenWrt package design.
- APPLIED same day: dropped the pstore→recovery diversion from U-Boot bootcmd
  on both routers (`fw_setenv bootcmd "run boot_ubi"`) so crashes self-heal
  when nobody is home; remote syslog now provides the diagnostics the
  diversion existed to preserve. An /etc/rc.local job archives pstore dumps
  to /root/pstore-archive/ on the next boot, clears them, and logs a
  user.crit alert. Verified with a clean reboot on each router. Recovery
  image remains reachable via reset button / U-Boot menu, and boot_ubi still
  falls back to recovery if the production image fails to load.
  Rollback: fw_setenv bootcmd "if pstore check ; then run boot_recovery ; else run boot_ubi ; fi"
- Crash context: house was empty, no heavy bandwidth use — weakens the
  load-triggered theory; idle/background paths equally suspect.
- Leading hypothesis after community research: marginal silicon at the
  mt7622's lowest DVFS operating point (437.5MHz, ondemand governor) —
  community-reported cause of idle spontaneous reboots on RT3200/E8450,
  fixed by raising the frequency floor. Fits: idle-time crashes, one unit
  of two identical affected, spans kernels 6.6→6.12, corrupt pstore.
- Experiment started: pinned scaling_min_freq to 600MHz on the downstairs
  (crashing) unit via rc.local, applied live without reboot; upstairs left
  at stock 437.5MHz/ondemand as the control. Verdict = months of uptime.
- Public repo audit: full-history scan for IPs/prefixes/MACs/keys/SSIDs
  found only the two items sanitized at HEAD (delegated IPv6 prefixes in an
  April note, LAN IP in a script comment); no secrets, no history rewrite.

2026-08-02: Firmware Upgrade 25.12.2 → 25.12.5 (+ silent sysupgrade failure RCA)
--------------------------------------------------------------------------------
- Upgraded both APs to 25.12.5 (kernel 6.12.74 → 6.12.94)
- Upstairs upgraded cleanly via LuCI Attended Sysupgrade; downstairs silently
  rebooted back into 25.12.2. Root cause: stage-2 `ubirmvol` of the `fit`
  volume can fail EBUSY (fitblk release contention during teardown) and
  fstools swallows the error (`|| :` in nand_upgrade_prepare_ubi), so the
  subsequent `ubimkvol` fails and the upgrade aborts with the old image
  intact — invisible without a serial console.
- Workaround that succeeded: stop heavyweight services (tailscale) first,
  then run sysupgrade from the CLI. Adopted as standard practice for the
  gateway router.
- Fixed a latent bug in the Tailscale IPv6 hotplug script (deploy_tailscale.sh):
  it parsed the default route with positional awk fields, which broke on
  source-constrained routes ("default from <prefix> via <gw>") — the exact
  route shape it was written to handle. Now parses by via/dev keywords.
  Confirmed working unattended on the post-upgrade boot.

2026-04-03: IPv6 Prefix Delegation Restored (DUID Fix) + DNS Cleanup
----------------------------------------------------------------------
- Fixed DHCPv6 prefix delegation by setting DUID to DUID-LL (type 3)
  matching the original ISP-supplied router
- Root cause: OpenWrt 25.12 changed DUID generation from per-interface
  DUID-LL (type 3, MAC-derived) to a global DUID-UUID (type 4). The
  BNG only serves PD to the DUID in its lease database, which had the
  old DUID-LL format. This was introduced by an Oct 2025 commit and
  affects anyone upgrading from 24.10 to 25.12.
- Enabled masq6 on the tailscale firewall zone for IPv6 exit node
- Disabled Tailscale MagicDNS on router (was hijacking resolv.conf
  with SERVFAIL responses); router now uses its own dnsmasq
- Set peerdns=0 on IPv4 WAN to ignore ISP DNS consistently
- Upstream DNS: Google Public DNS (8.8.8.8/8.8.4.4 + IPv6 equivalents)
- See notes/ipv6-duid-fix.md for full technical details
